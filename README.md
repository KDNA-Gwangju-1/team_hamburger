# team\_hamburger




이채호 : 저장과 커밋이 다른 점은 저장은 한번 하면 과거의 형상 혹은 형태로 돌아가기 어렵지만, 커밋은 기록이 남아서 해당 시점으로 돌아갈 수 있다. 이러한 기능 덕분에 오류나 에러가 나기 전 시점으로 돌아가거나, 시험적인 기능을 테스트할 수 있다.

최규용- 저장은 최종적으로 서버에 올리는 느낌이고 커밋은 서버에 올리기 전 최종 점검 느낌(저장하기 전에 마지막 확인)이다.

김석주
저장: 현 상황의 정보를 지정한 위치에 넣는것
커밋: 특정 구간에서 현 상황의 정보를 또 다른 위치에 넣는것

이도현 - 저장과 커밋을 둘다 파일을 온전한 상태로 보존해서 클라우드에 올린다는 것이 똑같지만 저장은 실시간으로 수정하기가 상당히 힘든 반면 커밋은 실시간으로 수정이 가능하다


김석주
1. 언제/왜 Pull을 먼저 했는지
과제에 대한 내용을 따라가서 내 순번일때 바로바로 push했으며, 이번 과제에서는 서로 소통하며 pull push를 했기에 안하면 어떻게 되는지에 대해서는 경험이 없기에 서술하기 어렵다. 

2. Commit 메시지 뭐라고 썻는지, Push 눌렀을 때 결과가 어땠는지
강의실 주변 음식 리뷰를 적었으며 처음에 충돌이 한번 일어났는데 강사님이 알려준 방법으로 메모장에서 수동으로 삭제해 충돌을 고쳐냈으며, 그 이후엔 Push를 눌럿을때 정상적으로 올라갔다. 

3.본인 차례를 기다리는 동안 다른 사람 화면에서 (혹은 GitHub Desktop History 탭에서) 뭐가 보였는지
내 차례를 기다리는 동안 다람 사람의 화면을 확인할 생각을 미쳐 하지 못했으며, 히스토리 탭에서는 갱신할때마다 
다른 팀원들이 갱신한 내용이 보였던거 같다. 





최규용


* 오늘(26.08.06) 과제를 하면서 Pull을 먼저 했다. Pull을 하니 다른 조원이 쓴 문서를 내가 이어서 쓸 수 있게 되었다.
* Commit 메시지에 조원끼리 정한 깃 커밋 컨벤션을 적었다. []안에 [add] 추가, [Doc]은 수정으로 [Doc] 최규용 채팅 추가 이런식으로 작성 하였다. Push를 눌렀더니 웹 서버에 내가 쓴 글이 올라온 걸 확인하였다.
* 내 차례를 기다리는 동안 History 탭을 보면 다른 사람이 수정한 것까지 다 보인다. 신기했다. 

\-채호

작성 후 수정한 파일을 올릴 때 푸시

다른 사람이 수정한 코드를 받아올 때 풀

커밋 메시지는 커밋 컨벤션과 간단한 수정내용에 따라 작성

내 차례를 기다리면서 다른 사람이 수정한 내용을 확인하기 위해서 fetch하고 커밋 메시지를 볼 수 있었습니다.
